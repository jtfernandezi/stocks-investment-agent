**1c. `pattern_performance` frozen since 07-21 — 2nd break in 3 weeks, caused by the last audit's own fix.**

The table's `updated_at` is `2026-07-21 05:29:33` on every row, despite **6 real closes since** (PLTR 07-23; AMAT, CHKP, NXPI, VRT 07-27; plus AXP/XOM 07-21). Recomputing from `trades` with the live node's exact `WHERE` clause shows what it should hold:

|---|---|---|
| TREND | 16 | 16 ✓ |
| BIAS | 6 | 6 ✓ |
| MOMENTUM | 4 | **5** |
| FIRST_SIGNAL | 4 | 4 ✓ |

The CHECK constraint is *not* the blocker this time — the 07-19 ALTER worked. The blocker is:
- `stocks.pattern_performance.pattern_type` is **`NOT NULL`**;
- one `trades` row has `entry_pattern = NULL` — **DELL**, the row hand-reconstructed per the 07-19 runbook §3, whose `INSERT` omitted `entry_pattern`;

This is the **4th instance** of this fund's signature failure: *a swallowed write error against a table nothing reconciles.* (2026-06-03 dropped column → cash deadlock; 2026-06-08 watchlist CHECK; 2026-07-19 pattern CHECK; now pattern NOT NULL.) **PR #30** adds the reconciliation that closes the class for this table; the 1-line SQL root fix is in the runbook.

### Lever 7 — Improvement 🟢

**7a.** The through-line this week is different from previous weeks and worth stating plainly. Every prior Lever-1 incident was a *monitoring gap* — something broke and nothing could see it. This week, **everything that broke was seen**: the canary caught the outage on day one and repeated itself for four days. The bottleneck has moved from detection to response.

Future data-correction runbooks should state the full column list and be followed by a verification query.
